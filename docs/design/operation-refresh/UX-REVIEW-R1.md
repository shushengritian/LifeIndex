## 主要发现

### B-R1-01 · P1 · 保存失败后面板位置随焦点变化，标题出屏、保存栏与字段交错

类型：**主代理定点复现的 UI 客观问题，B 独立看图确认**；优先修正编辑面板的识别与退出。已确认呈现/焦点状态关联，不等同已查明 CSS 或浏览器根因。

- 实际步骤（主代理，日志 #1–3）：今天 → 记一笔 → 金额 12.34、餐饮 → 关闭 → 继续编辑 → 正餐、日期 9月19日 → 注入一次保存失败 → 保存 → 失败返回。
- 实际：DOM 保留“记一笔”、关闭按钮、金额、分类、日期和错误提示，说明控件没有被删除。但在失败截图中，面板顶部直接从支出/收入开始，标题与关闭按钮不在可见范围；日期/时间控件露出上缘后即被保存栏截断，备注输入和错误提示却位于保存栏下方。不能把 DOM 中存在控件等同于视觉可达。
- 预期：失败时保留输入，错误可见，标题/关闭与底部保存仍形成稳定边界；日期、时间、备注在同一个内容滚动区内，不与保存栏交错。
- 定点复现（主代理提供，B 已实际看两图）：独立 index 浅色 `view=finance` → 记一笔 12.34、餐饮 → 注入失败 → 保存，使用 `fullPage:false` 再次得到标题/关闭出屏、保存栏上移、备注与错误在其下方的 [失败视口](../reviews/operation-refresh/finance-failure-repeat-r1.png)。随后主代理对“关闭编辑面板”执行 `press('Tab')`，焦点落到支出，得到 [焦点移回顶部后的视口](../reviews/operation-refresh/finance-failure-top-r1.png)：标题/关闭恢复，保存栏回到底部，金额与分类仍保留。
- 证据判定：不再以“可能只是整页拼接”保留候选；两次可见视口状态支持该问题随焦点位置出现/恢复。**不是永久无法关闭，也不是保存数据丢失。** 外层 1280×720 与主代理报告一致；内层 430×664 为主代理报告值，测量原始输出尚未核对，不把该尺寸当独立测量结论，也不外推全部尺寸。
- 根因边界：`app.js:294–298` 错误焦点处理、`app.css:158–165` 面板布局是核对位置；原生 fieldset 的 flex/滚动行为与 `error.focus()` 仅为可能线索，未确认因果。原始证据另见 [首次失败图](../reviews/operation-refresh/finance-failure-r1.png) 与日志 #3。
- 建议与 R2：修正失败焦点进入错误区时的面板滚动/布局，不增加替代弹窗。失败后标题/关闭与保存栏保持边界，内容可滚动、不与保存栏交错；焦点在错误、支出及关闭间移动不再改变面板结构，重试仍保留输入并成功。无需再补一轮集中 R1。

### B-R1-02 · P2 · 默认新增体重成功后，主摘要仍展示旧值

类型：**UI 客观问题，源码解释与现象一致**；影响保存结果确认。

- 实际步骤（主代理，日志 #5–7）：健康 → 记录体重 → 输入 68.1，保留默认 2026-09-20 07:30 → Escape → 继续编辑并保存。
- 实际：保存后焦点回到“记录体重”。曲线 DOM 已包含新值 68.1，但主摘要仍是 68.4 kg、9月20日 07:30；曲线终点也仍为 68.4。新记录存在，不是已证实的保存丢失。
- 预期：走默认新增路径后，结果应可辨认；同一时间有两条记录时应有确定、可理解的展示规则，不能让新增记录无声排在旧值之前、摘要看似未变。
- 证据：日志 #6、#7；`app.js:85` 样本已有同日 07:30 的 68.4，`:103` 仅按日期/时间排序，`:144–149` 曲线排序，`:157–160` 首项作为摘要，`:385–387` 新增默认 07:30 并追加记录。
- 建议与 R2：明确同时间记录的展示次序，或在成功反馈中直接定位新增记录；这是模拟结果呈现修正，不要求重建健康业务内核。重复原步骤，检查摘要、曲线和历史能一致解释新旧两条记录。

### B-R1-03 · P2 · 专注已结束待保存，最大读数仍突出“剩余时间”

类型：**有 UI 事实支撑的操作层级判断**；不是计时错误或数据丢失结论。

- 实际步骤（主代理，日志 #8–12）：开始 25 分钟专注 → 跨到健康再返回 → 提前结束 → 注入保存失败 → 查看待保存态 → 重试。
- 实际：失败时最大读数为“剩余时间 24:27”，圆环也保留运行中的进度形态；实际要保存的 00:33 位于下方小一层的“已专注”。“本次已结束”及失败解释在更下方。重试后确实出现一条“提前结束 · 33 秒”，次数由 1 增为 2，未保存时没有提前计入汇总。
- 预期：结束后的主要信息改为“本次结果 / 待保存”和实际时长，主要动作清楚指向保存；剩余与目标可以保留为次要信息。不要让用户先靠下方说明理解大倒计时已停止。
- 证据：[focus-pending-r1.png](../reviews/operation-refresh/focus-pending-r1.png)，日志 #10–12；`app.js:198–201` 对运行/待保存共用主读数，`:438–452` 保留待保存结果。
- 建议与 R2：只调整待保存态的信息主次，不添加暂停，也不删除提前结束/取消确认。复核失败→重试仍只新增一条，主读数表达实际结果。使用圆环还是其他容器属于偏好，不作为验收条件。

### B-R1-04 · P2 · 跨模块进入详情/管理后，“返回”不恢复来处

类型：**UI 客观问题；同类习惯路径另有源码事实。**

- 实际步骤（主代理，补充 #4–5）：设置 → 戒烟计划 → 计划管理 → 页头返回。
- 实际：返回后的页头为“戒烟”，出现计划经过、截至现在未吸烟和事件记录，不是刚才的设置。`app.js:181` 管理页把返回目标固定为 `health/cessation`，`:237` 设置入口却直接进入管理页。
- 同类源码事实：今天习惯文字行进入 `health/habit/:id`，详情页返回固定为 `health/habits`（`:126–139`、`:169`），不按今天入口返回。补充 #3 已展示习惯详情，但**未执行该页返回，不把此分支记成实操验证。**
- 预期：返回恢复来处与原位置。若希望导航到“戒烟概览/全部习惯”，应使用明确目的地语义，而不是无差别“返回”。
- 建议与 R2 步骤：保留详情/管理的入口上下文；设置进入管理后返回设置，戒烟页进入管理后返回戒烟页；同样核对今天进入习惯详情的返回。独立打卡仍保留，不合并为整行打卡。

### B-R1-05 · P2 · 设置允许创建专注/运动二级分类，但对应记录表单没有消费入口

类型：**源码直接证明的范围与操作语义不一致；尚未 UI 实操新增该子项。**

- 源码事实：四个分类分组共用一级详情与二级新增/保存处理，没有对专注/运动排除；但专注和运动的记录表单只映射一级分类，不展示二级项。用户可以创建一个无法在对应任务中选用的名称。
- 预期：管理入口应与已批准且可使用的分类层级一致。不能通过统一页面模板，暗示本轮新增了未接入记录流程的业务能力。
- 证据：`app.js:240–246` 四分组及统一二级入口，`:459–463` 子项保存；`:200`、`:424–426` 专注分类，`:392–394` 运动分类只使用根项。日志 #17 与 [category-menu-r1.png](../reviews/operation-refresh/category-menu-r1.png) 只证明分组和支出管理菜单存在，**不冒充专注二级已实测证据。**
- 建议与 R2 步骤：按本轮已批准范围收敛不适用的二级管理入口，而非要求实现专注/运动二级业务。检查设置 → 分类管理 → 专注/运动，与对应新增/编辑表单层级一致；记账的二级分类继续保留。
